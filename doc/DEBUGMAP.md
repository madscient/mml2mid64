# デバッグマップ `.mmlmap.json`

**形式バージョン 1**

`-g` を付けてコンパイルすると、出力 MIDI と並んで MIDI tick と MML ソース行の
対応表が出る。統合環境（[mml2mid64ide](../../mml2mid64ide)）が「再生位置に合わせて
ソース行をハイライトする」「カーソル行から再生する」ために使う。

**本ファイルがこの形式の正本である。** 消費側はここに書いてあることだけを前提に
実装すること。

## 使い方

```sh
mml2mid -g  song.mml        # song.mid と song.mmlmap.json が出る
mml2mid -g2 song.mml        # イベントテーブルも含める
```

| オプション | レベル | 内容 |
| --- | --- | --- |
| `-g` | 1 | 行テーブル（`lines`）のみ |
| `-g2` | 2 | 行テーブル＋イベントテーブル（`events`） |

- 出力先は MIDI 出力パスの拡張子を `.mmlmap.json` に差し替えたもの。
- 出力が `-`（stdout）のときはマップを出さず、警告を1行出す。
- `-g` を付けなければ**マップは生成されず、SMF も1バイトたりとも変わらない**。
  これは `test/dbgmap/` の各テストが毎回検証している。
- `CASE_INSENSITIVE_OPTS` が定義されたビルドでは `-G` は `-g` と同じ。
- 改行は常に LF、文字コードは入力ソースに従う（下記「文字コード」参照）。

## 形式

```json
{
  "version": 1,
  "generator": "mml2mid 5.30b (mml2mid64 fork)",
  "level": 2,
  "timebase": 48,
  "format": 1,
  "files": ["song.mml", "inc/part.mml"],
  "tracks": [
    {"index": 0, "kind": "tempo", "name": "",       "channel": -1},
    {"index": 1, "kind": "mml",   "name": "Melody", "channel": 0, "trackid": "0A"}
  ],
  "tempo": [[0, 500000], [96, 666667]],
  "lines": [
    [1, 0, 0, 2],
    [1, 192, 0, 3]
  ],
  "events": [
    [1, 0, 0, "on", 60, 100, 0, 2],
    [1, 47, 0, "off", 60, 0, 0, 2]
  ]
}
```

### トップレベル

| キー | 型 | 内容 |
| --- | --- | --- |
| `version` | int | この形式のバージョン。破壊的変更のたびに +1。**消費側は既知のバージョンだけ受理すること** |
| `generator` | string | 生成したコンパイラの識別文字列 |
| `level` | int | 1 = 行テーブルのみ、2 = イベントテーブルも |
| `timebase` | int | 4分音符あたりの tick 数（`#timebase`、既定 48） |
| `format` | int | 出力 SMF のフォーマット（0 または 1） |
| `files` | string[] | 参照されたソースファイル。`fileIdx` はこの配列への添字。`files[0]` はコマンドラインで与えた入力ファイル名 |
| `tracks` | object[] | 出力 SMF のトラック一覧 |
| `tempo` | array[] | `[tick, usecPerQuarter]`、tick 昇順。**level 1 でも必ず出る** |
| `lines` | array[] | 行テーブル。常に出る |
| `events` | array[] | イベントテーブル。level 2 のときだけ出る |

### `tracks`

| キー | 型 | 内容 |
| --- | --- | --- |
| `index` | int | 出力 SMF でのトラック番号（0始まり）。**0 は必ずテンポトラック** |
| `kind` | string | `"tempo"` または `"mml"` |
| `name` | string | `Cn"..."` で付けたトラック名。無ければ空文字列 |
| `channel` | int | MIDI チャンネル（0始まり）。`"tempo"` では -1 |
| `trackid` | string | MML 上の指定（従属トラック番号＋トラック名、例 `"0A"` `"1ML"`）。`"tempo"` では省略 |

`channel` は「そのトラックで最初のイベントを出した時点のチャンネル」であって、
トラック途中で `C` コマンドが変えた分は反映されない。**実際のチャンネルは
`events[]` の各要素が持つ値が正**。

`format` が 0 の場合、SMF 上のトラックは1本にマージされるが、`tracks` と `lines`
の `track` は**マージ前の論理トラック**を指す。絶対 tick はマージで変わらないので、
マップの内容は format に依存しない。

### `lines` — 行テーブル

```
[track, tick, fileIdx, line]
```

| 位置 | 内容 |
| --- | --- |
| 0 | `tracks[].index` |
| 1 | 絶対 tick（曲頭からの累積、`timebase` 単位） |
| 2 | `files` への添字 |
| 3 | ソース行番号（**1始まり**、`#include` 補正後の元ソース上の位置） |

- `(track, tick)` の昇順。
- **`(track, fileIdx, line)` が直前と同じエントリは畳まれる**（DWARF の行テーブル
  相当）。つまり「このトラックのこの tick から次のエントリまで、この行を演奏して
  いる」という区間の始点だけが並ぶ。要素数はおおむねソース行数×トラック数程度。
- 消費側は `(track, tick)` で二分探索し、直前のエントリを採る。
- **キーオフは行テーブルに入らない。** 「この tick ではこの行が鳴っている」を表すのが
  行テーブルの役目で、キーオフの位置はそれを歪めるだけ。キーオフは `events` にある。

### `events` — イベントテーブル（level 2 のみ）

```
[track, tick, channel, kind, d1, d2, fileIdx, line]
```

`channel` はチャンネルを持たないイベント（メタ、SysEx、テンポ、拍子）では -1。

| `kind` | `d1` | `d2` | 備考 |
| --- | --- | --- | --- |
| `"on"` | ノート番号 | ベロシティ | |
| `"off"` | ノート番号 | キーオフベロシティ | ベロシティ0のキーオンもこちらに分類する |
| `"ppres"` | ノート番号 | 圧力値 | |
| `"cc"` | CC 番号 | 値 | **RPN/NRPN もここに現れる**（CC 98/99/100/101/6 として） |
| `"prog"` | 音色番号 | 0 | バンクセレクトは別途 `"cc"` として出る |
| `"cpres"` | 圧力値 | 0 | |
| `"bend"` | 下位7bit | 上位7bit | |
| `"sysex"` | データ長 | 補助値 | 中身は持たない |
| `"meta"` | メタイベント種別 | データ長 | |
| `"tempo"` | 4分音符あたりのマイクロ秒 | 0 | |
| `"beat"` | 分子 | 分母 | 4分の4なら 4, 4 |

消費側は**未知の `kind` を黙って読み飛ばすこと**。将来の追加で壊れないように。

## 実装の要点（触る人向け）

実装は `src/dbgmap.c` / `src/dbgmap.h`。

**マップは後から導出できない。** SMF の出力はストリーム書き込み＋巻き戻し書き換え
（`write_length()` が控えた `lastlenpos` へ `fsetpos2` で戻る）で行われ、絶対 tick を
持ったイベント配列がどこにも作られないためである。よってイベントを書き出すその場で
`dbgmap_event()` を呼んで記録する。

巻き戻しの対象になるのは常に「まだイベントのバイト列が後続していない、宙ぶらりんの
デルタ」だけなので、イベント発行の時点で `tstep` を読めば確定した絶対 tick になって
いる。**`write_length()` にフックを置いてはならない。**

フックを置いてある隘路:

| 関数 | ファイル | 種別 |
| --- | --- | --- |
| `putnote()` / `putnoteoff()` / `ppres()` | `note.c` | ノートオン・オフ、ポリプレッシャー |
| `put_cntchange0()` | `mmlproc.c` | CC（RPN/NRPN もここを通る） |
| `put_bend0()` | `mmlproc.c` | ベンド |
| `put_cpres0()` ほか | `mmlproc.c` | チャンネルプレッシャー |
| `put_progchange()` ほか | `mmlproc.c` | プログラムチェンジ |
| SysEx / メタの書き出し | `mmlproc.c` | `EX` `mv` `mt`、トラック名、`W` 系 |
| `write_tmap()` | `mmlproc.c` | テンポ・拍子（`struct tmap` の絶対 tick から直接） |

ソース位置は `cur_line` ではなく **`cur_cmd_line` / `cur_cmd_file`**（`mmlproc.c`）を
使う。`cur_line` は先読み（`length()` や `getbyte(1)`）が行末を越えると先へ進んで
しまい、行の最後の音符が次の行のものとして記録されてしまう。`converttrk()` の
ディスパッチループでコマンドを取り出した直後に、`resolve_src_line()` で `#include` を
解決したうえで控えている。

`#include` の行・ファイル復元は `resolve_src_line()`（`charproc.c`）。`mml_err()` と
共有しているので、**片方だけ直すことがないように**。

## 既知の限界

いずれも設計上の割り切りであり、バグではない。

### 桁（column）は記録しない

コンパイラに桁の概念が一切存在しない。ハイライトは**行単位**になる。MML は1行に
多数の音符が並ぶので音符単位のハイライトはできないが、再生追従としては行単位で
十分実用になる。

将来足すなら: `track()`（`charproc.c`）に `cur_line` と並べて `cur_col` を置き、
`getLine_cooked()`（`mml2mid.c`）でコメント除去と `\` 行連結による「出力桁→元桁」の
変化点だけを記録して合成する。変化点は通常1行あたり0〜2個にしかならない。
マップ形式は `version` を 2 に上げること。

### マクロ本体の中身は呼び出し行に潰れる

- `$a` 形式のマクロは行情報を持たない平坦な文字配列として展開されるため、中身は
  すべて**呼び出し側の行**として記録される。
- `${name}` 形式は「1入力行＝1出力行」を保つ設計（`macroexp.c` 冒頭のコメント）なので、
  展開結果は**定義行ではなく参照が書かれた行**になる。

DWARF のインライン展開スタックに相当するものは持たない。必要になったら
`inlinedFrom` を足す拡張を検討する（`version` を上げること）。

### 従属トラックの位置合わせによる tick の飛び

従属トラックが主トラックに位置合わせする処理（`charproc.c`）で `tstep` が飛ぶことが
あり、その飛びはマップにもそのまま現れる。**演奏時刻としては正しい**ので、消費側で
補正してはならない。

### 文字コード

JSON 文字列中の 0x80 以上のバイトは入力の文字コードのまま通す。したがって
`-m`（MS漢字）で読んだソース由来のトラック名などは、妥当な UTF-8 にならない。
UTF-8 のソースを使う限り問題は起きない。

## テスト

`test/dbgmap/*.mml` と、それぞれの `.expected`（期待されるマップそのもの）。
`cmake/RunDebugMapTest.cmake` が各ファイルについて

1. `-g` 無しと `-g2` 付きで SMF のハッシュが一致すること（無害性の保証）
2. マップが `.expected` と一致すること

を検証する。`ctest -R dbgmap` で走る。

期待マップを更新するときは、生成物を**目で確かめてから** `.expected` に写すこと。

| テスト | 何を固定しているか |
| --- | --- |
| `notes` | tick と行の1対1対応。先読みで行がずれないこと |
| `loop` | `[ ]` 展開中も行番号が呼び出し行に戻ること |
| `include` | `#include` の行・ファイル復元、`files` が2件になること |
| `tracks` | 複数トラック、トラックごとに tick が0から始まること、トラック名 |
| `macro` | マクロ本体が呼び出し行に潰れること（上記の限界の固定） |
| `tempo` | テンポ・拍子がトラック0に載ること、`tempo` 配列 |

# 機械可読な診断 `--diag=json`

エラー・警告を、統合環境が `vscode.Diagnostic` へ変換できる形で出す。

```sh
mml2mid --diag=json song.mml song.mid
```

人間向けのメッセージに続けて、1エラーにつき1行の JSON オブジェクトを **stderr** へ
出す（`MSG_TO_STDOUT` 定義時は stdout）。`--diag=json` を付けなければ出力は従来と
まったく変わらない。

```json
{"severity": "error", "code": 64, "file": "song.mml", "line": 42, "message": "cannot interpret ','"}
```

| キー | 内容 |
| --- | --- |
| `severity` | `"error"` または `"warning"` |
| `code` | `err_msgs[]` / `warn_msgs[]`（`mmlproc.c`）の添字。プリプロセス段・マクロ展開段では 0 |
| `file` | ソースファイル名。判らない場合は入力ファイル名 |
| `line` | 1始まりの行番号（`#include` 補正後） |
| `message` | 人間向けメッセージから `ERROR!` / `Warning:` の接頭辞を除いたもの |

消費側は「`{` で始まり `}` で終わる行」だけを拾えばよい。

## エラー回復はしない

コンパイラ全体が「初回エラーで `exit`」を前提に書かれている（`mml_err()` →
`remove_file_and_owari()`）。**複数エラーを同時に報告することは構造上できない。**
警告は複数出る。

出力経路は3つで、すべて同じ形式:

| 関数 | ファイル | 段階 |
| --- | --- | --- |
| `prepro_msg_error()` | `mml2mid.c` | `getsp()` の前処理段。`me_err()`（マクロ展開段）もここを通る |
| `mml_err()` | `mmlproc.c` | コンパイル段。警告も含む |

テストは `test/diag/*.mml` と `.expected`（JSON 行のみ）。`ctest -R diag` で走る。
